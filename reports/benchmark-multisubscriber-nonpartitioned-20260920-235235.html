Method & caveats

Read the numbers above alongside these notes on how this benchmark was run.

  1. One trial per configuration. These are single runs, not averages across repeated trials; whether a given configuration produced violations can vary run to run, since it depends on the broker's real-time delivery timing and each message's randomized simulated work duration.
  2. The point of this run. The merged, cross-process ordering check found 9931 ordering violation(s) across 20000 messages handled - real reordering that the per-process check (which found 0) mostly or entirely missed, because it can only ever compare a message against others handled by that same process.
  3. How the global check works. OrderHandler logs a structured HANDLED OrderId=... Sequence=... line for every message. This script reads every instance's log file for a configuration's time window, merges all instances' events by timestamp into one true-arrival-order stream, and walks it checking that each key's Sequence strictly increases - exactly what a partitioned queue's per-process check already gets by construction, done here after the fact because nothing at the broker or client level provides it on a plain queue.
  4. Elapsed is measured by wall clock, from when the subscriber processes start consuming to when the broker (via SEMP) reports the queue fully drained - not any single instance's own tracked elapsed figure.
  5. Compare against the partitioned-queue report (see README > Comparing multiple subscribers) run at the same Count/KeyCount/instance-and-lane sweep: same throughput-scaling shape expected, but that report's ordering guarantee holds by construction, while this one's has to be checked for after the fact - and may or may not find anything, depending on timing.
