Method & caveats

Read the numbers above alongside these notes on how this benchmark was run.

  1. One trial per configuration. These are single runs, not averages across repeated trials; treat the curve as indicative, not a precise scaling law.
  2. Elapsed is measured by wall clock, not by summing per-instance figures. With multiple processes running concurrently, one instance's own first-to-last-handled span doesn't necessarily cover the whole run, so Elapsed is the time from when the subscriber processes started consuming to when the broker (via SEMP) reported the queue fully drained.
  3. Ordering. Every message's partition key is its OrderId (set on publish - see messaging-lab.orders.OrderKeySelector and SolaceMessageSender<T>'s optional partition-key selector), so the broker guarantees same-OrderId messages land in one partition and are therefore only ever seen by one subscriber process. Zero ordering violations across all 6 configurations (600 messages) - the partition key (OrderId) kept every key's messages inside one partition, and therefore one process, for the whole sweep.
  4. The idle-consumer ceiling. No configuration in this sweep exceeded PartitionCount=8 instances, so the idle-consumer ceiling wasn't exercised - rerun with a higher instance count to see it.
  5. Latency is a cross-instance range, not a merged percentile. Each instance computes its own p50/p99 independently over only the messages it personally handled; combining raw per-message latencies across processes to compute one true global percentile isn't done here, so Min p50/Max p99 should be read as a range, not a single statistic.
  6. The simulated handler cost is what makes this comparison meaningful. SimulatedHandlerWorkMinMs/MaxMs (250–1000 ms, uniform random) stands in for real per-message work — an external call, a database write.
